# Web Scan Watcher

Скрипт для автоматизации сканирования веб-приложений с поддержкой авторизации. Создает проект сканирования, запускает его и мониторит валидность авторизации на протяжении всего времени работы.

## Возможности

- Автоматическое создание и запуск проекта сканирования через API
- Периодическая проверка валидности авторизации в целевом приложении
- Автоматическая остановка сканирования при потере авторизации
- Валидация JWT-токенов перед запуском с предупреждением об истечении срока
- Поддержка секретов через переменные окружения (`env::VARIABLE_NAME`)
- Поддержка запуска нескольких экземпляров с разными префиксами окружения
- Автоматическое скачивание отчётов по завершении скана (PDF, HTML, JSON с алертами) для публикации в GitLab CI/CD artifacts

## Требования

- Python 3.11+
- Зависимости из `requirements.txt`

## Установка

```bash
pip install -r requirements.txt
```

## Быстрый старт

1. Скопируйте пример конфигурации:

```bash
cp config.example.yaml config.yaml
```

2. Отредактируйте `config.yaml` под ваши нужды

3. Установите переменные окружения:

```bash
export SF_TOKEN="ваш-api-токен"
export SF_APP_URL="https://sf.example.com"
```

4. Запустите скрипт:

```bash
python scan_watcher.py config.yaml
```

## Конфигурация

### Структура конфигурационного файла

```yaml
project:
  name: "my-web-scan"            # Имя проекта (обязательно)
  one_time: true                 # Одноразовое сканирование
  priority: 0                    # Приоритет (-1 до 3)
  scan_agent: ""                 # Агент сканирования (qtag). Пусто — агент по умолчанию
  # rps: 1000                    # Лимит запросов в секунду (30-10000). Не указан — не отправляется
  # ── Жизненный цикл: включите ЛИБО [A], ЛИБО любой из [B] (вместе → CONFIG_ERROR) ──
  # [A] переиспользовать существующий проект (поиск по имени):
  reuse_existing_project: false
  # [B] поведение для нового проекта — оба необязательны, порядок любой:
  delete_on_completion: false    # удалить проект после успешного завершения
  datetime_name_postfix: false   # добавить дату/время старта к имени проекта

target: "example.com"            # Цель: домен или IP-адрес

webauth:                         # Заголовки авторизации для целевого приложения
  Authorization:
    - "Bearer eyJhbGci..."
  Cookie:
    - "session=abc123"
    - "env::SESSION_TOKEN"       # Значение из переменной окружения

monitoring:
  # Включение health check авторизации в целевом приложении.
  # true  — периодически проверять валидность авторизации (по умолчанию)
  # false — полностью пропускать проверку (запросы не отправляются),
  #         health_check_url при этом не обязателен.
  enabled: true

  # URL для проверки валидности авторизации. Скрипт отправляет GET-запрос
  # с заголовками из webauth. Если ответ не входит в список разрешённых
  # кодов — сканирование останавливается.
  health_check_url: "https://example.com/api/me"

  # Список HTTP-кодов, которые считаются успешной авторизацией.
  # Любой другой код (401, 403, 500 и т.д.) означает потерю доступа.
  health_check_allowed_http_codes:
    - 200  # OK
    - 204  # No Content (некоторые API возвращают при успешной проверке)

  # Проверять TLS-сертификат health check URL (по умолчанию true).
  # false — отключить проверку для самоподписанных/просроченных сертификатов.
  verify_ssl: true

  check_interval_minutes: 5      # Интервал проверки (1-60)
  max_runtime_hours: 24          # Максимальное время работы (до 240)

report:
  language: "ru"                 # Язык PDF/HTML: "en" или "ru"
  severity: [10, 8, 5]           # Уровни угроз: 2 info, 3 low, 5 medium, 8 high, 10 critical
  pdf:
    enabled: true
    output_path: "./report.pdf"
  html:
    enabled: false
    output_path: "./report.html"
  alerts_json:
    enabled: false
    output_path: "./alerts.json"
  alerts_grouped_json:
    enabled: false
    output_path: "./alerts-grouped.json"
```

### Параметры проекта (`project`)

| Параметр                 | Тип    | По умолчанию | Описание                                                                           |
| ------------------------ | ------ | ------------ | ---------------------------------------------------------------------------------- |
| `name`                   | string | —            | Имя проекта (обязательно)                                                          |
| `one_time`               | bool   | `true`       | Одноразовое сканирование. При `true` скрипт завершится после завершения всех задач |
| `priority`               | int    | `0`          | Приоритет сканирования от -1 до 3. Чем выше — тем приоритетнее                     |
| `scan_agent`             | string | `""`         | Идентификатор агента сканирования (qtag). Пусто — использовать агент по умолчанию  |
| `rps`                    | int    | —            | Лимит запросов в секунду (30–10000). Необязательный, выключен по умолчанию         |
| `delete_on_completion`   | bool   | `false`      | Удалить проект после успешного завершения скана (после скачивания отчётов)         |
| `datetime_name_postfix`  | bool   | `false`      | Добавить к имени проекта дату и время старта в UTC (делает имя уникальным)         |
| `reuse_existing_project` | bool   | `false`      | Найти проект по точному имени и переиспользовать; если не найден — создать новый   |

#### Жизненный цикл проекта (создание / переиспользование / удаление)

По умолчанию каждый запуск скрипта **создаёт новый проект** через `POST /api/projects/`.

**`datetime_name_postfix: true`** — к имени проекта добавляется дата и время старта
в UTC, например `"my-web-scan 13 June 2026 12:44:07"`. Каждый запуск получает
уникальное имя, что удобно для хранения истории сканов.

**`reuse_existing_project: true`** — скрипт ищет проект по **точному** имени:

- если найден — переиспользует его и запускает **новое** сканирование в **любом** статусе проекта (через [`rescan`](#мониторинг-при-переиспользовании-rescan));
- если не найден — создаёт новый и запускает обычным `start`;
- на **каждом** запуске `scan_settings` и `scope` перезаписываются через `PATCH`
  (ротируемые webauth-токены, `priority`, `rps` всегда актуальны);
- если найдено **более одного** проекта с таким именем — скрипт завершается с
  ошибкой `CONFIG_ERROR`;
- **рекомендуется** `one_time: false` (см. [«Мониторинг при переиспользовании»](#мониторинг-при-переиспользовании-rescan) ниже).

**`delete_on_completion: true`** — удаляет проект (`DELETE /api/projects/{id}`)
**только** при успешном завершении скана, **после** скачивания
всех отчётов.

**Взаимоисключения:** `reuse_existing_project` несовместим с `delete_on_completion`
и `datetime_name_postfix`. Одновременное включение любой из этих комбинаций приводит
к ошибке `CONFIG_ERROR` при загрузке конфига.

##### Мониторинг при переиспользовании (rescan)

Переиспользуемый проект уже содержит завершённые задачи прошлых сканов, поэтому
в reuse-режиме проверка завершения работает по-особому — и **независимо от
`one_time`**:

- при старте запоминается базовое число задач проекта;
- пока **новые** задачи (от `rescan`) не появились — на каждом цикле пишется
  `WARNING` «новые задачи не были созданы», и скан **не** останавливается
  (мониторинг идёт до `max_runtime_hours`);
- как только число задач выросло — предупреждение прекращается;
- когда новые задачи **все завершились** — скан завершается штатно (проект
  останавливается, скачиваются отчёты);
- если новые задачи так и не появились — скан не останавливается раньше времени и
  доходит до `max_runtime_hours`.

Поэтому при переиспользовании **рекомендуется `one_time: false`**.

#### Ограничение скорости запросов (`rps`)

`rps` задаёт ограничение запросов в секунду.

Допустимый диапазон — от **30** до **10000**. Параметр **необязательный**: если он
не указан в конфигурации, то проект сканируется по умолчанию без ограничений. Указывайте `rps`, когда нужно ограничить нагрузку
на целевое приложение.

```yaml
project:
  name: "my-web-scan"
  rps: 1000   # не более 1000 запросов в секунду
```

### Цель сканирования (`target`)

Указывается одна цель — домен или IP-адрес:

```yaml
target: "example.com"
# или
target: "192.168.1.100"
```

### Заголовки авторизации (`webauth`)

Заголовки, которые будут использоваться:

- При сканировании целевого приложения
- При проверке валидности авторизации (health check)

```yaml
webauth:
  Host:
    - "example.com"
  Authorization:
    - "Bearer eyJhbGciOiJIUzI1NiIs..."
  Cookie:
    - "session=abc123; csrf=xyz789"
```

Каждый заголовок может содержать несколько значений

#### Секреты через переменные окружения

Для безопасного хранения токенов используйте префикс `env::`:

```yaml
webauth:
  Authorization:
    - "env::AUTH_TOKEN"  # Будет взято из $AUTH_TOKEN
  Cookie:
    - "env::SESSION_COOKIE"
```

**При использовании `--env-prefix` переменные также получат префикс:**

```bash
# С --env-prefix=RUN1__
# env::AUTH_TOKEN будет искать $RUN1__AUTH_TOKEN
```

### Мониторинг (`monitoring`)

| Параметр                           | Тип       | По умолчанию | Описание                                                   |
| ---------------------------------- | --------- | ------------ | ---------------------------------------------------------- |
| `enabled`                          | bool      | `true`       | Включить health check авторизации. `false` — проверка полностью пропускается (запросы не шлются) |
| `health_check_url`                 | string    | —            | URL для проверки авторизации (обязателен при `enabled: true`) |
| `health_check_allowed_http_codes`  | list[int] | `[200]`      | HTTP-коды, означающие успешную авторизацию                 |
| `verify_ssl`                       | bool      | `true`       | Проверять TLS-сертификат health check URL                  |
| `check_interval_minutes`           | int       | `5`          | Интервал между проверками (1-60 минут)                     |
| `health_check_retries`             | int       | `2`          | Повторов health check при транзиентных сетевых/TLS ошибках |
| `health_check_retry_delay_seconds` | float     | `5`          | Задержка между повторами health check (секунды)            |
| `max_runtime_hours`                | float     | `24`         | Максимальное время работы (до 240 часов = 10 дней)         |

#### Health Check URL

URL, на который будет отправляться GET-запрос с заголовками из `webauth`. Если ответ содержит HTTP-код не из списка `health_check_allowed_http_codes`, сканирование будет остановлено.

**Транзиентные сетевые ошибки** (таймаут, ошибка TLS-рукопожатия, обрыв) не считаются мгновенной потерей доступа: проверка
повторяется `health_check_retries` раз с задержкой `health_check_retry_delay_seconds`
секунд, и скан останавливается только если **все** попытки неудачны. Каждая неудачная
попытка логируется (`ERROR` с текстом ошибки). Увеличивайте число/задержку ретраев при нестабильной сети.

Рекомендуется использовать эндпоинт, требующий авторизации, например:

- `https://example.com/api/version`

#### Отключение проверки (`enabled: false`)

По умолчанию `enabled: true` — health check выполняется. Установите
`enabled: false`, чтобы **полностью отключить** проверку: скрипт не отправляет
никаких запросов на `health_check_url`, авторизация всегда считается валидной, а
сам `health_check_url` в этом случае указывать не обязательно.

```yaml
monitoring:
  enabled: false            # health check выключен, health_check_url не нужен
  check_interval_minutes: 5
  max_runtime_hours: 24
```

Отключение уместно для **неавторизованных** сканов (публичная цель без `webauth`),
где проверка авторизации не имеет смысла и может ложно оборвать скан (например,
если целевой WAF отвечает 403/429). Для авторизованных длительных сканов проверку
лучше оставить включённой — она вовремя ловит протухшую сессию.

### Отчёт (`report`)

Секция необязательна. Поддерживаются четыре формата отчёта — `pdf`, `html`,
`alerts_json` (JSON с алертами) и `alerts_grouped_json` (JSON со сгруппированными
алертами). Любая комбинация может быть включена одновременно — каждый формат
сохраняется в свой `output_path`.

Отчёты охватывают **только текущий запуск**

```yaml
report:
  language: "en"            # язык PDF/HTML: "en" или "ru"
  severity: [10, 8, 5]      # уровни серьёзности: 2=INFO,3=LOW,5=MEDIUM,8=HIGH,10=CRITICAL
  pdf:
    enabled: true
    output_path: "./report.pdf"
  html:
    enabled: false
    output_path: "./report.html"
  alerts_json:
    enabled: false
    output_path: "./alerts.json"
  alerts_grouped_json:
    enabled: false
    output_path: "./alerts-grouped.json"
```

#### Фильтрация по уровню серьёзности (`severity`)

| Значение | Уровень  |
| -------- | -------- |
| `2`      | INFO     |
| `3`      | LOW      |
| `5`      | MEDIUM   |
| `8`      | HIGH     |
| `10`     | CRITICAL |

По умолчанию: CRITICAL, HIGH, MEDIUM.

#### Когда отчёты скачиваются

| Ситуация                                         | Скачивается? |
| ------------------------------------------------ | ------------ |
| Успешное завершение скана (все задачи выполнены) | ✔            |
| Превышение `max_runtime_hours`                   | ✔            |
| Получение `SIGINT` / `SIGTERM`                   | ✔ (попытка)  |
| Потеря авторизации в целевом приложении          | ✔ (попытка)  |

Отчёты скачиваются (best-effort) во всех случаях остановки, **включая потерю
авторизации** — чтобы не терять уже найденные результаты. Отчёт тянется из SF API
(не из цели), поэтому потеря доступа к цели ему не мешает. При ошибке скачивания
(сетевой сбой, недоступность API) скрипт логирует ошибку, но не меняет итоговый exit
code — поведение скана приоритетнее (при потере авторизации он остаётся `AUTH_FAILURE`).

## Переменные окружения

| Переменная   | Описание                                     |
| ------------ | -------------------------------------------- |
| `SF_TOKEN`   | API-токен для авторизации в SF (обязательно) |
| `SF_APP_URL` | Базовый URL API SF (обязательно)             |

При использовании `--env-prefix` переменные в таблице выше должны иметь соответствующий префикс:

```bash
# Для --env-prefix=RUN1__
export RUN1__SF_TOKEN="..."
export RUN1__SF_APP_URL="..."
```

### TLS-сертификаты (`SSL_CERT_FILE`, `SSL_CERT_DIR`)

Если целевое приложение использует сертификат, подписанный собственным
(корпоративным/внутренним) удостоверяющим центром, который отсутствует в системном
наборе доверенных CA, укажите путь к файлу сертификата (CA bundle в формате PEM)
через переменную окружения `SSL_CERT_FILE`:

```bash
export SSL_CERT_FILE="/path/to/my_certificate.pem"
```

- `SSL_CERT_FILE` **заменяет** встроенный набор доверенных CA (`certifi`), а не
  дополняет его. Файл должен содержать все необходимые корневые/промежуточные
  сертификаты. Если помимо внутреннего CA нужны и публичные, добавьте свой
  сертификат в копию связки `certifi` и укажите путь к ней.
- При `monitoring.verify_ssl: false` проверка сертификата для health check
  полностью отключается, и `SSL_CERT_FILE` на него не влияет. Чтобы проверять
  самоподписанный сертификат, а не игнорировать его, оставьте `verify_ssl: true`
  и задайте `SSL_CERT_FILE`.
- Каталог с сертификатами можно указать через `SSL_CERT_DIR` вместо `SSL_CERT_FILE`.
- На `SSL_CERT_FILE` и `SSL_CERT_DIR` `--env-prefix` **не** распространяется — это
  стандартные переменные httpx/OpenSSL, читаются как есть, имя всегда без префикса
  (т.е. ✅ `SSL_CERT_FILE`, а не ❌ `RUN1__SSL_CERT_FILE`).

## Интеграция с GitLab CI/CD

По завершении скана скрипт скачивает включённые форматы отчётов в пути, указанные
в `report.<format>.output_path`. Эти файлы можно опубликовать как артефакты пайплайна.

Пример `.gitlab-ci.yml`:

```yaml
web_scan:
  image: python:3.11-slim
  variables:
    SF_TOKEN: $SF_TOKEN        # передать через CI/CD variables
    SF_APP_URL: $SF_APP_URL
  script:
    - pip install -r web_scan_watch/requirements.txt
    - python web_scan_watch/scan_watcher.py web_scan_watch/config.yaml
  artifacts:
    paths:
      - report.pdf             # совпадает с report.pdf.output_path
      - alerts.json            # совпадает с report.alerts_json.output_path
    when: always              # сохранить артефакт даже при ненулевом exit code
    expire_in: 30 days
```

Укажите в `artifacts.paths` пути всех включённых форматов — они должны совпадать
со значениями `output_path` из конфига.

## Коды завершения

| Код | Константа      | Описание                                             |
| --- | -------------- | ---------------------------------------------------- |
| 0   | `SUCCESS`      | Сканирование завершено успешно или graceful shutdown |
| 1   | `AUTH_FAILURE` | Авторизация стала невалидной                         |
| 2   | `CONFIG_ERROR` | Ошибка конфигурации или валидации токенов            |
| 3   | `API_ERROR`    | Ошибка при работе с API                              |

## Валидация JWT-токенов

Скрипт автоматически анализирует JWT-токены в:

- `SF_TOKEN` (API-токен)
- Значениях `webauth` (токены авторизации приложения)

Если токен истекает раньше, чем `max_runtime_hours`, будет показано предупреждение:

```
============================================================
  WARNING: Token Expiration Risk
============================================================

• API token (SF_TOKEN) expires in 12.5 hours, but max_runtime_hours is 24
• Token in webauth.Authorization expires in 8.0 hours
```

## Логика работы

1. **Создание проекта** (или переиспользование при `reuse_existing_project: true`)
2. **Запуск сканирования**
3. **Периодический мониторинг и health check**
4. **Остановка сканирования**
5. **Скачивание отчётов** (включённые форматы, если авторизация не была потеряна)
6. **Удаление проекта** (только при `delete_on_completion: true` и успешном завершении)

## Выключение scan_watcher

При получении сигналов `SIGINT` (Ctrl+C) или `SIGTERM` скрипт прерывает мониторинг и останавливает сканирование проекта, завершаясь с кодом 0.

Обратно включить сканирование проекта можно в ЛК.

Повторный запуск с тем же конфигом зависит от режима:

- **обычный режим** (создание нового проекта): запуск с уже использованным `name`
  упрётся в существующий проект. Варианты: поменять `name`; либо включить
  `datetime_name_postfix: true` (имя станет уникальным на каждый запуск); либо
  удалить старый проект в ЛК.
- **режим переиспользования** (`reuse_existing_project: true`): повторный запуск с
  тем же конфигом — это штатный сценарий. Скрипт находит проект по имени и
  перезапускает сканирование через `rescan` (менять имя или удалять проект не нужно).

## Определение завершения сканирования

- **`one_time: true`** (обычный режим): скан завершён, когда все созданные задачи
  выполнены (активных не осталось, есть завершённые) — после этого проект
  останавливается.
- **`one_time: false`** (обычный режим): завершение по задачам не проверяется —
  скан идёт до `max_runtime_hours`.
- **Режим переиспользования** (`reuse_existing_project: true`): завершение
  проверяется **независимо от `one_time`** и по-особому — скан ждёт **новые**
  задачи от `rescan` и завершается, только когда они все выполнены; пока новых
  задач нет — мониторит до `max_runtime_hours`
  (подробно — [«Мониторинг при переиспользовании»](#мониторинг-при-переиспользовании-rescan)).

В любом режиме скан также останавливается при превышении `max_runtime_hours`,
по `SIGINT`/`SIGTERM` или при потере авторизации.

## Решение возможных проблем

### Ошибка "Environment variable X is not set"

Убедитесь, что переменная экспортирована:

```bash
export SF_TOKEN="..."
# Проверка
echo $SF_TOKEN
```

При использовании `--env-prefix` не забудьте добавить префикс к переменным.

### Health check всегда failing

1. Проверьте, что `health_check_url` доступен и требует авторизации
2. Убедитесь, что заголовки в `webauth` корректны
3. Проверьте список `health_check_allowed_http_codes` (если стабильно приходит,
   например, 404 вместо 200 — проверьте URL/маршрут или добавьте нужный код)
4. При ошибке TLS — проверьте сертификат: для внутреннего/самоподписанного CA
   задайте `SSL_CERT_FILE` (или временно `verify_ssl: false`)
5. Запустите с `--log-level=DEBUG` для подробного вывода

### Токен истёк во время сканирования

Скрипт автоматически остановит сканирование при первой неуспешной проверке авторизации. Для минимизации потерь:

- Используйте токены с большим сроком жизни
- Уменьшите `max_runtime_hours` до времени жизни токена
- Уменьшите `check_interval_minutes` для более быстрого обнаружения

### Режим переиспользования: скан не завершается / постоянно `WARNING` «новые задачи не были созданы»

В режиме `reuse_existing_project: true` скан завершается только после того, как
`rescan` создаст **новые** задачи и они выполнятся. Если на каждом цикле в логах
`WARNING` про отсутствие новых задач — значит rescan их пока не породил. Что
проверить:

1. Запрос `POST /rescan` прошёл успешно (см. лог запуска)
2. `target`/`scope` и `scan_agent` валидны — иначе сканеры не создают задачи
3. Дайте время: задачи появляются не мгновенно. Скан не остановится сам, пока их
   нет, и дойдёт до `max_runtime_hours`

Это поведение защищает от ложного «завершения» на старых задачах переиспользуемого
проекта.

### Ошибка `CONFIG_ERROR` при запуске

Частые причины:

1. Одновременно включены взаимоисключающие опции: `reuse_existing_project` вместе с
   `delete_on_completion` или `datetime_name_postfix`
2. В режиме `reuse_existing_project` найдено **более одного** проекта с таким именем
   (имя должно быть уникальным)
3. Не заданы обязательные переменные окружения (`SF_TOKEN` / `SF_APP_URL`) или
   ошибка в YAML
4. Невалидные значения: `severity` вне набора `2,3,5,8,10` или `rps` вне диапазона
   30–10000
